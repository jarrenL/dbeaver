# 日期时间边界验证

## 范围与执行方式

对应历史清单 11.1 日期时间、金融行业日期时间精度场景。使用现有 GaussDB 507 集中式和分布式真实实例以及项目使用的 JDBC 驱动，不使用模拟结果集。测试方法为 `GaussDBHistoricalJdbcLiveTest.timestampJdbcPreservesDistinctInstantsAcrossDaylightSavingTransitions`，参数化执行两种部署形态。

在随机隔离 schema 内创建带时区时间戳表，通过 `PreparedStatement.setTimestamp` 和 UTC Calendar 插入四个微秒精度时间点及一行 SQL NULL，再依次切换会话时区 America/New_York、UTC、Asia/Shanghai 读取。测试不修改 JVM 默认时区，也不修改其他会话；结束后清理隔离 schema。

| 边界 | 输入 UTC | 纽约本地预期 |
|---|---|---|
| 春季切换前 | 2024-03-10 06:59:59.123456 | 01:59:59.123456 |
| 春季切换后 | 2024-03-10 07:00:00.123456 | 03:00:00.123456 |
| 秋季重复时间第一次 | 2024-11-03 05:30:00.123456 | 01:30:00.123456 |
| 秋季重复时间第二次 | 2024-11-03 06:30:00.123456 | 01:30:00.123456 |

每个时区下逐行断言 JDBC `getTimestamp(..., UTC).toInstant()` 与原始 Instant 完全相同，验证两个同名本地时间仍对应不同时间点、微秒不丢失。纽约显示通过服务端格式化结果独立核对。NULL 行同时验证 JDBC 时间戳、格式化文本及 `wasNull()`，并检查无多余行。

## 边界

本轮是 JDBC 数据往返测试，不替代 DBeaver GUI 日期格式、操作系统时区、Excel 日期格式或客户版本验收。没有验证不存在/歧义本地时间输入时的默认解析策略；输入使用明确 UTC 时间点，避免将隐式策略当作跨版本保证。24 个跳过用例不算通过，完整历史清单仍未全部闭环。

# 认证 profile 安全存储字段隔离

## 为什么单独验证

配置扁平序列化与 DBAAuthProfile.persistSecrets/resolveSecrets 是不同实现。后一条路径将扩展字段存入独立 properties 对象，不能从前一条路径的缺陷推断它同样存在覆盖问题。

本轮使用生产 profile 序列化/反序列化，以及内存模拟 DBSSecretController。所有凭据均为虚构内容，不访问实际钥匙串或读取真实密码。

## 三项新增场景

- 保存主密码开/关两种情况：扩展属性也包含 user/password，另含中文、单双引号、换行和反斜杠；写入 JSON 后检查主字段不被替换，重新读取后主凭据及扩展属性分别保持原值，源属性不被修改。
- 两份 profile 采用不同存储 key，分别写入；第一份关闭主密码保存并更新后，第二份原记录完全不变，仍能恢复其用户名/密码。

**重要边界：**关闭保存主密码只禁止顶层 password。本实现仍保存 properties 中的自定义秘密字段，包括同名的嵌套 password；其是否应该随主密码开关清除属于扩展认证策略，不在本轮声称覆盖的范围。测试只证明结构隔离，并非“所有秘密都不会保存”。

本轮不修改生产代码，也不将模拟存储测试当作真实加密文件、系统钥匙串或 GUI 开关验收。

## 结果

`run-Mffnzp` 三项新增用例通过，整套新鲜结果 1438 项、1414 通过、24 跳过、0 失败/错误。临时授权角色已删除。[脱敏逐例报告](test-results-20260924-auth-field-isolation.json)。

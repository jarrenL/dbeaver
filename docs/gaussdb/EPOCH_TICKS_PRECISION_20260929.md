# .NET ticks / Windows FILETIME 精度回归

## 对应场景和范围

历史场景清单的时间转换与结果值显示/编辑。DBeaver Epoch转换器在界面配置中已公开dotnet、w32filetime单位，本轮直接验证这两个生产转换分支。

这是平台中立的Java时间转换测试，**不代表Windows操作系统安装、文件权限、进程或GUI验收通过**。

## 12项场景

每种单位分别验证以下六项，每项先检查精确显示文本，再检查文本解析返回相同long整数：

1. 该单位零点：.NET的0001-01-01、FILETIME的1601-01-01。
2. 该单位零点加1 tick，即100纳秒。
3. Unix零点加1 tick，显示1970-01-01 00:00:00.0000001。
4. Unix零点减1 tick，显示1969-12-31 23:59:59.9999999。
5. Unix零点加1234567 ticks，显示七位小数.1234567。
6. Unix零点加10000001 ticks，验证跨秒后的.0000001。

测试位于平台模块EpochTimeAttributeTransformerTest；属性和会话使用替身，实际转换逻辑来自生产类，不模拟转换结果。

## 复现和修复

修复前12项中10项失败，两个单位的整数零点本来通过。共用格式器使用`nnnnnnn`（纳秒数字字段），100纳秒显示为.0000100，而秒小数应为.0000001；Unix零点前的值还会出现九位小数。日志：`/tmp/epoch-ticks-red-20260929.log`。

共用格式器改为`SSSSSSS`（七位秒小数），保留严格日历解析和原有100纳秒换算算法。

最终结果以[逐项测试证据](evidence/EPOCH_TICKS_REACTOR_20260929.json)为准。诊断命令执行73模块中的五个测试模块，允许失败后继续收集结果；验收仍由独立门禁判断，不能把Maven的SUCCESS当成验收通过。日志：`/tmp/epoch-ticks-green-20260929.log`。

Epoch专项**40/40通过，零跳过**。五模块合计**2595项：2421通过、173跳过、0失败、1错误**；唯一错误仍为RestTest本地网络权限拒绝，独立门禁正确拒绝整体通过。Docker访问同样被拒，本轮没有真库或Linux GUI新增验收通过结果。

## 未覆盖

整数极限/溢出、各平台日期取值限制、历史时区规则、儒略日和OLE小数精度、真实数据库写回以及GUI操作不在本轮通过范围内。修正小数显示会改变旧版本错误显示的小数文本；旧显示文本并非可靠的精确时间导出格式，不能据此宣称旧文本数据自动迁移正确。

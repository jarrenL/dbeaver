# 兼容凭据存储替换验证

对应清单 3.12/3.13/10.3 的配置持久化、密码清除和对象隔离。直接调用生产 `DataSourceParser.saveSecuredCredentials`，传入隔离内存的 ContextParameters 和虚构密码。数据源/profile 身份为 mock，不修改客户文件。

## 场景

| 场景 | 输入、操作与预期 |
| --- | --- |
| 替换连接凭据 | 先保存主密码和 token，再保存无主密码、仅 realm 的凭据；旧 password/token 都必须消失，用户名和新 realm 保留。 |
| 单节点清理 | 同连接保存数据库和 ssh 两个节点，另外创建独立连接；清空数据库节点，只移除它，隧道密码及其他连接逐值不变。 |
| 最后节点清理 | 清空唯一节点，顶层连接记录也移除；再次清空不生成空记录。 |
| profile 替换 | profile 使用独立 profile: 前缀 key；移除密码后只保留用户名，不误写数据源 key。 |
| 新安全存储模式 | project.isUseSecretStorage=true 时不写兼容记录，已有无关记录不变。 |

## 发现与修复

`run-CtYjF0` 5 项中 4 项失败：生产逻辑复用旧属性 map 并追加，因此遗漏的密码/token 不删除，空凭据也清不掉旧节点。检查现代序列化器发现 secureProperties 可从现有记录加载并用于后续保存，不能假定它始终为空。

改为先生成完整新凭据 map，再替换当前子节点；新 map 为空则移除子节点，顶层空时沿用已有清理逻辑。其他连接和兄弟节点不变。不会扫描或删除任何宿主机文件。

## 边界

这是兼容凭据 map 更新路径的组件测试，不代表加密文件实际覆盖、异常断电恢复、用户界面或 Windows 权限已经验证。历史记录在后续成功保存时更新，不宣称所有既有密码已自动迁移清除。认证属性与 user/password 保留字段冲突仍需独立审计。发布客户端尚未同步本轮 registry 修复。

## 最终结果

`run-QICTYu` 新增 5 项全部通过，全量已配置回归 **1,365 项 / 1,341 通过 / 24 跳过 / 0 失败错误**，各报告新鲜度已校验。[脱敏结果](test-results-20260924-credential-replacement.json)。运行包含既有 507 集中式/分布式 JDBC 场景；本组凭据组件测试没有使用数据库密码。临时 grantee 已删除。

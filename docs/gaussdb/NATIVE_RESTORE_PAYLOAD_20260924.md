# 原生备份恢复的数据完整性验证

## 环境及入口

GaussDB 507集中式隔离测试库，厂商gs_dump/gsql/gs_restore实际进程。测试类为`GaussDBNativeLiveTest`，显式启用`GAUSSDB_REVIEW_NATIVE=true`并提供私有连接属性文件与JDBC路径。身份、数据库命名及端口经过防误操作校验，测试schema不存在后才运行。密码通过生产handler的标准输入管道传递，不写入报告。

测试采用生产恢复handler的进程配置和密码传递逻辑；命令行由测试构建，不代表已验证所有向导选项或整条任务调度/UI链路。

## 执行流程

1. 在隔离schema创建3行整数基础表及2行多类型表。
2. gs_dump生成普通SQL备份，将约4MB查询输出附在脚本后；删除测试schema，通过gsql恢复。生产重定向将标准输出丢弃，核对正常退出且数据恢复完整。
3. gs_dump生成自定义归档，再删除测试schema，gs_restore恢复并再次核对数据。
4. 恢复脚本先除零再DELETE，ON_ERROR_STOP使其失败且后续DELETE不执行；验证原3行仍在，错误输出不包含测试密码。
5. 改为合法INSERT重试，4行合计10。
6. finally删除本次测试schema和随机命名的备份/日志文件，不保留客户数据或秘密，不删除用户备份。

## 新增数据断言

### 空二进制和较大二进制增补

多类型表现为4行：在原2行之外增加非NULL的零长度bytea，以及固定种子生成的1 MiB+3字节伪随机bytea。后者同时校验长度与SHA-256，覆盖普通SQL、归档、仅结构/数据组合以及错误拒绝/合法重试的所有既有恢复检查点。避免只核对长度漏掉内容破坏，也不将整块二进制写入日志。

先执行 `verifyPayload` 建立备份前基线，再调用实际工具。零长度夹具由服务端 `substring(decode('00','hex') from 1 for 0)` 生成，不依赖JDBC空字节绑定。新增后 `run-MzXhjh` 全部通过：1870项、1854通过、16跳过、0失败错误，见 [较大二进制结果](native-large-binary-results-20260924.json)。方法数未增加。结束后独立检查review_native及临时调试角色成员均0。

**同时发现的独立缺口，未修复：** 初次 `run-Qhs9Ux` 空bytea断言失败。独立厂商JDBC实验在同一集中式测试连接中创建临时表，对照服务端表达式写入与 `PreparedStatement.setBytes(new byte[0])` 写入。前者 `v IS NULL=false, octet_length(v)=0, getBytes长度=0`；后者 `v IS NULL=true, octet_length(v)=NULL, getBytes=NULL`。连接关闭删除临时表。因此失败发生在备份前的JDBC写入，而非恢复造成；不能以调整恢复夹具宣称空二进制写入兼容性已经解决。需继续核对DBeaver值处理器、厂商驱动绑定格式及各兼容模式，并补专门回归。

2026-09-24 后续增补：多类型表新增 bytea、TRUE/FALSE 两个布尔列。二进制逐字节验证 `00 01 7F 80 FF`；第二行 NULL bytea 必须仍为 NULL。布尔不仅检查 `getBoolean` 返回值，还立即检查 `wasNull`，明确区分 FALSE 与 NULL。相同断言在普通 SQL、自定义归档、结构/数据分离恢复、损坏归档拒绝后的保留数据及合法重试之后执行。

原用例重新启用回归 `run-U8JtU5` 通过；增加上述断言后 `run-myQeSn`：1,870 项执行、1,854 通过、16 跳过、0 失败错误，见 [二进制与布尔恢复结果](native-binary-results-20260924.json)。扩充同一测试方法不增加方法计数。该批次同时显式启用六项包/调试真库测试；临时调试角色最终撤销。

结束后独立 SQL 检查：review_native 及另外五个测试 schema 合计 0，测试账号调试角色成员关系 0。测试 finally 删除精确随机命名的合成备份及日志（不可恢复，不涉及用户备份）。GUI 向导、分布式原生工具及空集群 gs_dumpall 仍不计通过。

普通SQL和自定义归档分别核验：

- 中文文本含单引号、反斜杠、换行、制表符，完整逐字相等。
- numeric(38,9)值`12345678901234567890.123456789`，BigDecimal精确相等。
- timestamp(6)闰日值`2024-02-29 12:34:56.001234`，微秒未丢失。
- 第二行文本、数值、时间均NULL；行顺序及恰好两行。

这些断言扩充既有测试方法，不以一个方法计数代表仅一条数据场景，也不虚增JUnit数量。

## 仅结构与仅数据组合恢复增补

在同一隔离schema完整恢复后，分别执行实际`gs_dump --data-only -F c`和`gs_dump --schema-only`。保留数据归档到测试临时目录，删除schema，先用gsql恢复仅结构文件，确认两张表均0行；随后用gs_restore导入数据归档，复核全部多类型值。

再次插入重复主键得到23505，插入NULL主键得到23502；失败后原有两行数据不变，验证恢复的不只是列名，还保留主键和非空约束。没有使用`--clean`或全库删除选项；所有删除仅限本次新建的review_native测试schema。

## 损坏归档及正常归档重试

将合成的无效归档交给真实gs_restore，要求有界时间内以非零结果失败，stderr不含测试密码。独立JDBC核对多类型表原值不变；随后仅清空测试表，使用此前保存的合法data-only归档再次恢复并核对全部值。该场景不把超时当作预期失败，也不推断任意中途损坏归档都具有事务原子性。

首次run-Gs7eTx中工具已非零退出，但测试额外要求stderr非空未满足。该厂商工具在本场景没有stderr文本，生产恢复路径丢弃stdout，本轮移除不适用的“stderr必有文本”假设，不把该假设失败记作服务端恢复成功或产品已修复。用户界面能否提供足够的失败诊断仍需独立验证。

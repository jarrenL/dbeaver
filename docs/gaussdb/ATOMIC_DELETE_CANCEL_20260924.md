# 批量删除执行中取消：锁等待验收

## 复现

麒麟V10 x86_64客户端，模型/导航插件202609232338，GaussDB507分布式测试库。重新创建独立三表夹具。gsql独立事务以 `application_name=dbv_atomic_cancel_lock_20260924` 锁定第二张表，设置120秒自动结束期限，不锁业务对象。

970–973在导航树选择first和second，确认仅两表；974执行。独立pg_locks显示first的AccessExclusiveLock已获取、second的AccessShareLock等待以及测试会话的AccessExclusiveLock已获取。976观察底部“取消当前操作”按钮；977点击，978确认按钮禁用，但独立锁状态仍显示删除在等待。

测试锁到期释放后，979显示“原子保存已取消”，独立查询first=11、second=22、keep=33。**回滚数据正确，但及时取消阻塞SQL未通过**，不能把按钮禁用当作取消成功。980关闭错误框，显式删除三张测试表和专用schema。

## 原因与修复方向

新批量路径使用 `UIUtils.runInProgressService`；该接口源码明确说明阻塞I/O不能取消，只设置进度监视器取消标记。原子保存因此只能等SQL返回后检查取消并回滚。

已改为 `AbstractJob` 执行同一隔离事务工作。该框架取消任务时会收集活动的 `DBRBlockingObject`，通过异步取消器调用JDBC语句取消。继续使用独占连接、整体保存、最终关闭连接，不增加逐对象重试。错误返回任务错误状态并显示整体诊断，不吞掉失败。

修复后仍须构建并在新插件上重跑相同锁等待场景：必须在锁尚未释放时观察删除等待消失、数据回滚及UI恢复，才能确认及时取消通过。当前文档不宣称修复后的GUI验收已经完成。

构建回归run-RiCW41：1563项/1540通过/23跳过/0失败错误；没有以既有单测代替新增GUI取消断言。收尾独立确认专用schema和持锁测试会话数量均为0。

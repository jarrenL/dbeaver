# Epoch 日期合法性与时区往返

## 场景

接续[微秒精度回归](EPOCH_MICROSECONDS_20260929.md)，对应历史清单日期时间转换、结果值编辑验证，新增15项生产转换器测试：

| 场景 | 方法与预期 |
| --- | --- |
| 八种单位的非闰年2月29日 | seconds、milliseconds、microseconds、nanoseconds、dotnet、w32filetime、oadate、sqliteJulian；按各自格式输入2023-02-29，必须抛出带日期解析原因的DBCException |
| 无效日期与时刻 | 秒单位输入2024-02-30、2024-04-31、24:00:00、秒数60，必须拒绝，不能静默调整 |
| 失败后的合法输入 | 上述每项拒绝后，以同一转换器显示再解析该单位的数值0，检查结果仍为0；包括儒略日零点对应的公元前年份 |
| 非UTC微秒往返 | 上海、加德满都、圣约翰斯三个时区，将1709251199123456显示为精确的六位小数本地时间，再解析回相同整数；包含非整点时差和跨日 |

测试文件为平台模块的EpochTimeAttributeTransformerTest。无需数据库；通过真实转换器和模拟属性/会话验证，不是模拟日期转换结果。

## 发现与修复

修复前新增场景11项失败，错误日历输入未抛出异常；秒数60已拒绝，三个时区往返原本通过。红测日志：`/tmp/epoch-calendar-red-20260929.log`。

根因是DateTimeFormatter默认SMART解析策略。八种单位共用的六个格式器统一使用STRICT，并将年份字段由year-of-era（yyyy）改为proleptic-year（uuuu），让严格解析无需额外era，同时保留公元前年份符号。其他单位的小数字段和数值转换算法没有在本轮修改，不声称其所有精度边界已验证。

专项28项首次修复验证全部通过；补齐空值注解后另跑最终回归，结果以[逐项证据](evidence/EPOCH_CALENDAR_REACTOR_20260929.json)为准。运行范围是73模块中的五个测试模块，不是完整发行包。日志：`/tmp/epoch-calendar-final-20260929.log`。

测试类已加入必跑类列表，缺失或跳过会导致验收门禁拒绝；门禁自测7/7通过，该计数不算DBeaver功能场景通过数。

最终专项仍为**28/28通过、零跳过**。五模块合计**2583项，2409通过，173跳过，0失败，1错误**。唯一错误为RestTest网络操作被权限拒绝；诊断运行保留继续执行选项以收集后续模块结果，独立门禁仍拒绝整体通过。跳过项不算通过，不累加前几轮的重复用例。

## 剩余边界

本轮不证明DST不存在/重复本地时间的编辑策略、整数溢出、各非Unix单位的小数精度、GaussDB JDBC时间类型绑定或最新Linux界面整包验收。Docker访问被拒，未产生新的真库/GUI通过结果。

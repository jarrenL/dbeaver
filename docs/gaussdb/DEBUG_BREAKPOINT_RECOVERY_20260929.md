# 调试断点：部分成功后的状态与重试

## 需求对应与新增场景

原始需求“设置、启用、禁用、删除断点”，历史清单的断点推送和异常恢复。本轮新增4项生产GaussDBDebugSession测试：

| 场景 | 断言 |
| --- | --- |
| 初始禁用断点添加成功、禁用失败 | 保留已注册编号0及已启用状态；随后禁用重试确实再次发送SQL，成功后转为禁用 |
| 初始禁用断点正常注册 | 禁用命令执行期间仍是已启用状态；只有返回成功才更新为禁用；重复禁用不再次发送 |
| 重复添加时删除旧断点失败 | 保留原对象和编号，不执行新add；显式重试成功后只保留新编号7 |
| 删除旧编号成功、添加新断点失败 | 客户端注册列表为空；重试直接添加新编号8，不再删除已经失效的旧编号0 |

## 发现与修复

初始红测中2项断言失败，复现同一个生产缺陷：add_breakpoint成功后，客户端仍沿用用户请求的disabled状态。若后续disable_breakpoint失败，再次调用disable会误判“已经禁用”而直接返回。

修复是在添加成功后记录服务端已启用状态，再执行用户要求的禁用；禁用成功才更新状态。失败时保留已确认的注册和状态，供后续显式重试。

另有1项红测错误来自测试替身：重复查询使用已耗尽的ResultSet。为重试重新准备游标后修正，**不将该错误计作生产缺陷**。删除旧编号成功后添加失败的路径原实现已满足测试要求。

红测日志：`/tmp/debug-breakpoint-recovery-red-20260929.log`。回归日志：`/tmp/debug-breakpoint-recovery-green-20260929.log`。完整结果见[逐项证据](evidence/DEBUG_BREAKPOINT_RECOVERY_REACTOR_20260929.json)。

## 证据边界

使用真实生产会话方法和Mockito JDBC异常注入，验证命令次数、绑定编号、注册对象身份和状态迁移。不是实际网络断线，也不能证明“服务端执行成功但响应丢失”时的远端状态。初始禁用失败仍向上层报告错误；本轮不宣称界面自动重试、自动恢复或异常提示验收通过。

完整回归为73模块中的五个测试模块。诊断构建允许错误后继续执行以收集结果，独立门禁仍拒绝任何测试错误，不将跳过算成通过。

最终GaussDBDebugSessionTest **46/46通过、零跳过**。整轮**2607项：2433通过、173跳过、0失败、1错误**；唯一错误为RestTest本地网络权限拒绝，独立验收门禁拒绝整体通过。Docker访问也被拒，本轮未增加真库或Linux GUI通过结论。

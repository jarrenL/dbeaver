# 客户端小数秒精度验证

## 问题

历史清单要求日期时间精度、数据编辑和结果显示。本轮直接检查 `DateTimeDataFormatter` 对旧版小数秒格式 `f` 的转换。

旧实现将任意长度的 `f` 转成单个 `n`，把“小数秒”变成“纳秒整数”。例如毫秒格式 `.fff` 的 `.001` 应代表 1 毫秒，而纳秒整数解析会产生不同的时间值；格式化也不再保证三位小数。此外全局替换会修改引号内的 `fff` 字面文本。

修复将未引用的 `f` 逐位转换为 Java 时间格式的 `S`，保留 3/6/9 位精度及前导零；引号内文本保留。显式 `n` 格式没有改写。

## 用例与证据

`DateTimeDataFormatterLocaleTest` 新增四项：

- 三种小数秒位宽：3、6、9。每种分别输入 0、1,000,000、123,456,789 纳秒；验证 LocalDateTime 与显式 UTC 的 JDBC Timestamp 显示一致，宽度和前导零正确。
- 同一组文本分别按显式 LocalDateTime 和自动类型解析，结果精确等于按所选位宽截断后的时间，禁止把小数秒当纳秒整数。
- 带引号 `'fff'` 的格式保持原始文本，并对 `.001` 正确往返。

修复前 `run-i2YJVL` 四项全部失败。失败运行不作为未执行模块的新鲜证据。

## 边界

修复后 `run-x8mLQ4`：四项新增测试及本类其他 16 项全部通过；整套新鲜结果 1401 项、1377 通过、24 跳过、0 失败/错误。临时真库授权角色已删除。[脱敏逐例结果](test-results-20260924-date-fraction.json)。

本轮验证生产格式器，不代表 GUI 日期显示设置和数据保存流程已全部验收。对于小于九位的小数，格式化按配置截断而非四舍五入；这与旧 `ExtendedDateFormat` 的位宽含义一致。可选小数、自定义超长位宽和全部历史格式组合需要另测。

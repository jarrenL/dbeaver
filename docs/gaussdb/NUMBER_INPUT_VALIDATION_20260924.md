# 数字输入完整性验证

## 发现

对应历史清单数值类型精度、数据编辑及工具转换。直接测试生产 `NumberDataFormatter`，不以数据库 numeric 存储验证替代客户端输入解析。

`run-hVQHcM` 新增九项测试中四项复现失败：`123abc`、`123.45junk`、`1;DELETE`、`12 34` 均只解析前面的数字，忽略尾部。空文本和完全非数字原本拒绝。这里的注入形状输入没有执行 SQL；问题是静默截断输入。

## 修复

使用 ParsePosition 核对所有字符均已消费，未完整解析时抛出 ParseException，并携带失败位置。错误文本不包含原始数值。区域数字格式及既有数值类型转换策略不变。

## 用例

- 六种非法输入分别检查 BigDecimal 类型提示和无类型提示。
- 38 位有效数字的 BigDecimal 直接解析，精确相等，不能经 Double 损失精度。
- 美国 `1,234.50`、德国 `1.234,50` 都解析为同一 BigDecimal；`1.23E5` 保持科学计数法支持。
- Long 最小值、Integer 最大值保留；格式化 NULL 返回 NULL。

## 边界

修复后 `run-XbdLQw` 九项新增测试均通过，整套新鲜结果 1420 项、1396 通过、24 跳过、0 失败/错误。临时授权角色已删除。[脱敏逐例报告](test-results-20260924-number-input.json)。

完整消费检查不等于分组符位置的严格语法检查，也未处理整数收窄转换溢出。本轮不是 GUI 输入提示或实际网格保存验收；后续需核对调用方是否绕过或降级解析。拒绝此前被忽略的尾随文本属于有意行为变化。
